# Смена цвета — новая физическая нить (C1)

Проект 23.09.2026, задача 9 [ночной очереди](../docs/night-queue.md); строка C1
[матрицы способностей](kiku-capabilities.md). Код этим документом не меняется.

## Ремесло

Цвет нити не меняется по ходу: новый цвет — это новая нить. Старую заканчивают
(скрытое закрепление и обрезка), новую вводят отдельно (GT14: «Enter a length of
Color B on a marking line…»; третий цвет финишного круга — тоже новая нить).
Парковка (park) — другое: та же нить откладывается и продолжается тем же концом.

## Как сейчас в коде

- `traceKagariOperations`: `threadId = <рецепт>/p<полюс>/s<группа>` — цвет в
  идентичность не входит; тест `kagari-topology.test.ts` («keeps the same physical
  thread when A is parked for B or changes colour») закрепляет это прямо.
- `groupWorkingThreads` собирает цепочки по полюсу и группе, рендер тянет одну
  трубку через смену цвета.
- Интерфейс («Нити»): «Меняется цвет следующих стежков выбранной нити» — обещает
  перекраску той же нити дальше по ходу, чего не бывает.

## Предлагаемое

1. **Идентичность:** `threadId = …/p<полюс>/s<группа>/n<номер нити>`; номер растёт,
   когда у операции другой цвет, чем у предыдущей операции той же группы.
2. **Концы:** прежняя нить получает `finish` на своём последнем порту (скрытый
   проход, обрезка), новая — `start` на линии разметки перед первым стежком.
   `resume` только внутри одной нити.
3. **Рендер и метраж:** цепочки по `threadId`; у старой нити закопанный конец,
   у новой — выход из намотки; метраж считается по нитям.
4. **Тест:** смена цвета даёт новую `threadId` с `previousInThread = null`,
   у прежней — последняя операция; парковка A на время B нить не меняет.

## Решения владелицы (до кода)

- Текст в «Нитях»: вместо «меняется цвет следующих стежков» — «следующий стежок
  начнёт новую нить этого цвета». Ведение интерфейса — за владелицей (#98).
- Где вводить новую нить по умолчанию: на линии разметки у следующего стежка
  (как GT14) — предлагается так.
